## 1. 為什麼要做

本機除錯與驗收時，元素存量、已學會的魔法、關鍵道具、擊殺數都只能直接改本機 D1 的存檔 JSON，又慢又容易寫壞。使用者想要一個 GM 工具，最常用的是**改元素數量**，其次是**解鎖地圖**與**查完整配方表**【使用者決定】。正式上線後也要能用，但**必須驗證是使用者本人的帳號密碼**【使用者決定】；上線前必做的「管理員重設密碼」也併進這個工具【使用者決定】。

**目標**：
- 邊玩邊調整：在遊戲畫面裡叫出 GM 視窗，改完立刻看到效果【使用者決定】。
- 本機與正式上線用同一套驗證與同一份程式碼。
- 玩家忘記密碼時，GM 能安全地重設，不需要手動算雜湊、手動下 SQL。

**非目標**：
- 一鍵學會所有魔法（使用者要的是配方表，不是全學會）【使用者決定】。
- 改其他玩家的存檔、封鎖或刪除玩家、查看其他玩家的存檔內容【我的決定，依第 3 節規則推得】。
- 多個 GM 角色與權限分級；GM 名單以外的任何人都沒有 GM 功能【我的決定】。

**反目標**：
- 一般玩家能叫出或使用 GM 功能（包括猜到快捷鍵、直接打 API）。
- GM 改過的存檔被防作弊誤判、之後每次上傳都被拒。
- 用過 GM 的帳號拿到稀有魔法首位發現者或排行榜名次。
- 重設密碼時明文密碼經過伺服器或留在紀錄裡。
- 在原本的遊戲畫面上加任何 GM 按鈕或入口【使用者決定：「不要附加在原先的畫面上」】。

## 2. 開啟方式與外觀【使用者決定：草圖 A】

- 遊戲畫面上沒有任何 GM 按鈕。按 **Ctrl＋Shift＋`**（數字 1 左邊那個鍵；遊戲常見的「主控台」鍵）叫出或關閉 GM 視窗。不用 Ctrl＋Shift＋G，因為那是瀏覽器「尋找上一個」的快捷鍵，可能被瀏覽器攔走。備用入口：網址加上 `?gm` 時，載入後直接打開 GM 視窗（萬一快捷鍵在某個鍵盤配置上按不出來）。【我的決定】
- GM 視窗是浮在遊戲上方的小視窗（紫色邊框，與遊戲配色區隔），可以拖曳標題列移動、縮小成只剩標題列、按 ✕ 關閉；位置與縮小狀態記在這台裝置的 `localStorage`（讀寫要 try/catch）。【我的決定：紫色、記住位置】
- 遊戲在 GM 視窗開著時照常進行。
- 第一次打開（或 GM 驗證過期）時，視窗內只有一個登入表單：**帳號名稱＋密碼**。驗證通過後才顯示分頁。
- 不是 GM 的帳號按快捷鍵：只會看到登入表單；登入失敗一律顯示「帳號或密碼錯誤」，不透露該帳號是不是 GM。
- 窄螢幕（手機）不需要支援拖曳，但視窗要能完整操作（例如固定在畫面下方、可捲動）。【我的決定】

## 3. 誰是 GM、能做什麼【使用者決定，第 3 輪確認】

- **GM 名單**放在伺服器設定 `GM_USERNAMES`（逗號分隔的帳號名稱；本機寫在 `.dev.vars`，正式上線用 `wrangler secret put GM_USERNAMES`），不寫在程式碼裡。比對方式與登入相同（`usernameKey`：NFKC＋小寫）。【使用者決定：本機與上線都驗證帳密；我的決定：放在 secret】
- `GM_USERNAMES` 沒有設定或為空時，所有 GM 端點回 **404**，功能等於不存在。這個檢查在 session 驗證**之前**，所以未設定時連未登入的請求也是 404，不會從 401／404 的差別看出功能存不存在。`GM_USERNAMES` 從 `worker/index.ts` 的 `Env` 傳進 `createApp` 的 deps，測試以注入的方式設定。【我的決定】
- **改存檔的功能只作用在 GM 自己的帳號**（目前登入的那個帳號）；**重設密碼是唯一能碰到其他玩家的功能**。
- **用過任何改存檔功能的帳號**，被標記為「GM 帳號」：之後不能成為稀有魔法的首位發現者（等同第二版 B 對可疑帳號的處理：照常學會、不寫入 `discoveries`、回應 `rare.first = false`），也不參加之後的排行榜。只看配方表或只重設別人密碼，不會標記。
- **配方表只在通過 GM 驗證後顯示**。注意：遊戲內容（含 `recipes.json`）本來就打包在前端 JS 裡（用戶端模擬戰鬥需要），所以這只是介面上不給一般玩家看，**不是**安全邊界；這點與第二版 B「資訊欄不公布配方」相同，記為已知限制。【我的決定，必須告知使用者】
- **每次 GM 操作都留下紀錄**（誰、何時、做了什麼、對象），只寫入、不提供刪除。

## 4. 驗證流程【我的決定】

- GM 驗證是**一般登入之外的第二道確認**：玩家必須已經以該帳號登入遊戲（有一般 session），在 GM 視窗**再輸入一次帳號與密碼**。
- 密碼照現有方式處理：瀏覽器用 `clientPasswordHash(帳號, 密碼)` 算出雜湊後送出，伺服器 `verifyPassword`（HMAC＋pepper）比對；明文密碼不離開瀏覽器。
- 伺服器確認三件事：帳號在 `GM_USERNAMES`、帳號屬於目前 session 的玩家、密碼正確。所以 GM 必須先用一般流程以**已綁定帳號**登入遊戲；遊客永遠不能當 GM。通過後發一個 **GM token**（隨機 32 bytes，只存雜湊），有效 **30 分鐘**，綁定該玩家；之後的 GM 請求同時帶一般 session 與 `X-GM-Token`。
- 登入失敗沿用現有的登入失敗限制（同帳號、同 IP 的次數上限與 Retry-After），不另設一套。
- GM token 只存在記憶體（React state），重新整理頁面就要重新驗證；不寫進 `localStorage`。
- 登出、改密碼時，該玩家的 GM token 一併作廢。

## 5. 分頁【使用者決定：第 4 輪確認】

### 5.1 元素（含素材、關鍵道具）
- 5 屬性 × 5 階級的表格，每格可以直接輸入數量或按 ＋／－；下方列出所有素材與關鍵道具，同樣可改。
- 按「套用」才送出（一次送出所有改動），伺服器把存檔的 `inventory` 改成指定數量（0～999999 的整數；0 代表移除）。
- 套用後用戶端以伺服器回傳的存檔取代本地狀態（和合成等伺服器動作相同），戰鬥不中斷。

### 5.2 地圖
- 「開放所有地點」：`unlockedZones` 設為全部地點。
- 「散開所有迷霧」：`revealed` 設為所有可散開的區域（不消耗關鍵道具）。
- 「把目前地點設成差 1 隻出魔王」：`zoneKills[目前地點] = killsForBoss - 1`。【我的決定，使用者同意】
- 「擊敗目前地點的魔王」不做；要測魔王就用上一項再實際打。【我的決定】

### 5.3 配方表
- 列出 `recipes.json` 的所有配方：兩個輸入（名稱）、結果（名稱，含 Lv.）、機率（權重換算成百分比；落空到自創魔法的那部分寫「落空 → 自創魔法」），以及兩個魔法融合時需要的元素（用引擎的 `fusionNeeds`，依 GM 自己目前的狀態計算）。【我的決定，使用者同意】
- 上方一個搜尋框，用魔法名稱或元素名稱篩選；稀有魔法標上「稀有」。
- 純用戶端計算（內容本來就在前端），不需要伺服器端點。

### 5.4 玩家（重設密碼）
- 輸入玩家的**帳號名稱**，按「重設密碼」：
  1. GM 視窗在瀏覽器產生一組**臨時密碼**（12 個字元，英數混合，排除容易看錯的字元），用 `clientPasswordHash(該帳號, 臨時密碼)` 算出雜湊；
  2. 送出帳號名稱與雜湊；伺服器 HMAC 後寫入該帳號的 `password_hash`，並**刪除該玩家所有 session 與 GM token**；
  3. 臨時密碼**只在 GM 視窗顯示一次**（附「複製」按鈕），請 GM 轉交玩家；伺服器與紀錄裡都沒有明文。
- 帳號不存在時顯示「找不到這個帳號」（GM 已通過驗證，告訴 GM 帳號是否存在不是洩漏）。遊客沒有帳號名稱，所以本來就無法被重設。
- 重設時**一併清除該帳號的登入失敗紀錄**（`u:<usernameKey>`），否則忘記密碼、連錯好幾次而被暫時鎖住的玩家，拿到臨時密碼也要等一小時。【我的決定】
- **不能重設自己**（請用帳號視窗的「改密碼」），也**不能重設 GM 名單裡的帳號**；兩者都回 403 `{ error: 'not_allowed' }`。【我的決定】
- `gm_actions.target` 記正規化後的帳號名稱（`normalizeUsername` 的結果）。
- 這取代上線前檢查清單第 2 節的手動流程與必做項目；檢查清單改成「上線前用 GM 工具在本機 D1 測一次重設」。

## 6. 伺服器與資料【我的決定】

- migration `0006_gm.sql`（**不能重置存檔**）：

```sql
ALTER TABLE players ADD COLUMN gm_used INTEGER NOT NULL DEFAULT 0;

CREATE TABLE gm_tokens (
  token_hash TEXT PRIMARY KEY,
  player_id TEXT NOT NULL REFERENCES players(id),
  expires_at INTEGER NOT NULL
);

CREATE TABLE gm_actions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  gm_player_id TEXT NOT NULL REFERENCES players(id),
  at INTEGER NOT NULL,
  action TEXT NOT NULL,      -- 'login' | 'inventory' | 'unlock_zones' | 'reveal_all' | 'boss_ready' | 'reset_password'
  target TEXT,               -- 被重設密碼的帳號名稱；其他動作為 NULL
  detail TEXT                -- JSON，例如改了哪些道具；絕不含密碼或雜湊
);
```

- 端點（全部要一般 session；除了登入以外都要 `X-GM-Token`；`GM_USERNAMES` 未設定時全部 404）：
  - `POST /api/gm/login` `{ username, password }`（`password` 是瀏覽器雜湊）→ `{ gmToken, expiresAt }`；失敗 403（與一般登入相同的錯誤碼與限制）。
  - `POST /api/gm/inventory` `{ items: Record<ItemId, number> }` → `{ state, revision }`
  - `POST /api/gm/zones` `{ op: 'unlock_all' | 'reveal_all' | 'boss_ready' }` → `{ state, revision }`
  - `POST /api/gm/reset-password` `{ username, password }`（臨時密碼的瀏覽器雜湊）→ `{}`；帳號不存在 404。
- **改存檔的動作**沿用現有伺服器動作的流程（`serverAction`／`checkUpload`）：請求帶著用戶端目前的狀態與 `baseRevision`，先照常稽核（422／409 的處理與合成相同），再把 GM 的變更套在**稽核過的用戶端狀態**上，通過 `parseState` 後寫回（revision＋1）。這樣還沒同步的擊殺與掉落不會被丟掉，戰鬥也不會倒退。
- 寫回時**防作弊錨點直接設成新存檔、錨點時間設為現在**（不是一般動作的「扣掉花費」），讓之後的上傳以 GM 改過的狀態為基準，不會因為增益過大或 `key:` 道具不是打魔王來的（R8）而被拒；`audit.ts` 本身不需要改。同時把 `players.gm_used` 設為 1。
- `items` 裡不認得的道具 id（不符合 `ITEM_ID_RE`、或內容裡沒有的素材／關鍵道具）回 400；數量必須是 0～999999 的整數，否則 400。
- 合成稀有魔法時（第二版 B 的 onCommit），`gm_used = 1` 的玩家比照可疑帳號：照常學會、不寫 `discoveries`、`rare.first = false`。`gm_used` 刻意和 `suspicious` 分開：`suspicious` 是防作弊判定的「可能作弊」，`gm_used` 是「GM 自己動過存檔」，意義不同、之後也可能要分開處理；伺服器加一個共用判斷（例如 `excludedFromRecords(player) = suspicious || gmUsed`），發現紀錄與之後的排行榜都只看它。
- 每個 GM 端點成功後寫一筆 `gm_actions`；登入失敗不寫（已由登入失敗限制記錄）。
- `Store` 介面加對應方法，`MemoryStore` 與 `D1Store` 都實作，加進 `store-contract.ts` 契約測試；`tests/d1` 加 migration 0006 測試（套用後舊存檔與玩家都在、`gm_used` 預設 0）。

## 7. 不能違反的規則（摘自 `AGENTS.md` 第 6 節，與本次相關）

- **伺服器是銀行**：GM 改存檔一樣是伺服器動作；用戶端只能請求，不能自己改了再上傳。
- **防作弊錨點**：GM 改存檔後錨點要跟著前進（第 6 節），`tests/sim` 各路線仍 0 次被拒、worker 對抗測試全部通過。
- **遊客 token 只在 401 時清除**：GM token 過期回 401 時只清 GM token，不能清掉一般 session（用不同的錯誤碼，例如 `{ error: 'gm_expired' }` 403，避免觸發一般 session 的 401 流程）。
- **不收集 email**；介面文字繁體中文；「Lv.」只代表階級。
- **部署前要先取得使用者同意**；`GM_USERNAMES` 與 pepper 一樣是上線前要設定的 secret，寫進上線前檢查清單。

## 9. 驗收

1. 未設定 `GM_USERNAMES`：所有 `/api/gm/*`（含未登入的請求）回 404；按快捷鍵只看到登入表單，登入失敗。
2. 設定後，以 GM 帳號登入遊戲、按 Ctrl＋Shift＋`（或網址加 `?gm`）、輸入帳密 → 看到四個分頁；非 GM 帳號用正確帳密 → 「帳號或密碼錯誤」。
3. 元素分頁改數量（含一個關鍵道具）並套用 → 元素表立刻更新、戰鬥不中斷、套用前剛打到的掉落還在；之後 60 秒正常遊玩、上傳不被拒；`players.gm_used = 1`。
4. 地圖分頁三個按鈕都生效（地點選單出現全部地點、迷霧散開、目前地點顯示差 1 隻出魔王）。
5. 配方表列出所有配方與機率，搜尋可用，融合需求與合成台一致。
6. 玩家分頁重設另一個帳號的密碼：舊密碼不能登入、臨時密碼可以登入（即使該帳號之前因連錯被暫時鎖住）、該玩家原本登入的裝置都被登出；請求內容與 `gm_actions` 都沒有明文密碼；重設自己或其他 GM 帳號回 403。
7. `gm_used = 1` 的帳號合出稀有魔法時不成為首位發現者、不上資訊欄。
8. GM token 30 分鐘後過期 → GM 視窗回到登入表單，一般遊戲不受影響。
9. 遊戲畫面上沒有任何 GM 入口；`npm test` 與 `npm run build` 通過。
