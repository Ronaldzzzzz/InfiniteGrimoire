## 1. 為什麼要做

路線文件的原始構想：機率很低的合成結果要有「首位發現者」與「最近發現動態」，讓全服玩家知道有人摸索出稀有魔法。

使用者描述的那一刻【使用者決定】：

> 他會看到一個全屏全新的魔法動畫。其他玩家會在資訊欄出現消息。

追問後發現：照使用者的「稀有」條件（高階＋透過機率取得），目前全遊戲只有聖光審判、深淵吞噬兩個魔法符合，而且都在很後期。所以這次同時**新增 5 個稀有魔法**。

**目標**：
- 合出稀有魔法是一件全服都會知道的事：發現者有專屬的全螢幕動畫，其他人在資訊欄看到消息。
- 首位發現者被永久記下來（顯示留給之後的排行榜）。
- 稀有魔法值得追：比同時期的一般魔法更強一點。

**非目標**【使用者決定】：
- 排行榜頁面（第二版 C+D）。這次只把首位發現者**存起來**，之後做排行榜時再顯示。
- 改動任何現有的魔法或配方。稀有魔法是額外內容，「特殊的魔法比較特殊，但不會影響原先的魔法」。

**非目標**【我的決定】：即時推播（WebSocket）；資訊欄用輪詢即可。不做「我的發現」個人頁。

**反目標**：
- 公布配方（資訊欄與紀錄只能有魔法名稱、殘卷線索、發現者顯示名稱）。
- 新內容卡住或改變專精路線：`tests/sim` 各條純屬性路線的通關時間仍要落在 60～240 模擬分鐘、0 次被拒。
- 作弊帳號上榜或刷消息。
- 套用 migration 時重置存檔（0004 已經重置過一次；這次不能再重置）。

## 2. 稀有魔法的規則【使用者決定】

- **每種屬性各一個，共 5 個。**
- **只能透過機率配方取得**，而且配方至少要用到**高階（第三階）元素**。
- 平均嘗試 **50～80 次**才會合出一個。
- 威力比同時期的一般魔法**更強一點**。
- **落空時和現在完全一樣**：照常落到該組合的自創魔法（已經會了就照 R14 的重複規則扣成本），合成台播一般的特效。

### 2.1 五個稀有魔法【我的決定，使用者交給設計者】

| 屬性 | id | 名稱（nameEn） | 配方 | 結果 |
|---|---|---|---|---|
| 火 | `worldfire` | 焚世之焰（Worldfire） | `inferno` ＋ `el:fire:3` | 1 : 49 |
| 風 | `heavens_breath` | 蒼穹之息（Heaven's Breath） | `vacuum_blades` ＋ `el:wind:3` | 1 : 49 |
| 雷 | `ninefold_thunder` | 九天雷獄（Ninefold Thunder） | `myriad_thunder` ＋ `el:thunder:3` | 1 : 49 |
| 土 | `titans_grip` | 泰坦之握（Titan's Grip） | `landslide` ＋ `el:earth:3` | 1 : 49 |
| 水 | `moontide` | 滄溟月潮（Moontide） | `maelstrom` ＋ `el:water:3` | 1 : 49 |

- 「1 : 49」是 `recipes.json` 的權重：稀有魔法 `weight: 1`、`spellId: null`（落到自創魔法）`weight: 49`，成功率 1/50 = 2%，平均 50 次，在使用者要的 50～80 次之間。（2026-10-24 使用者指示「稍微提高機率」：原本 1 : 64、平均 65 次。）
- 配方的第一個輸入是各屬性 Lv.5 的純屬性魔法（煉獄、真空刃、萬雷、山崩、大漩渦），第二個輸入是**高階元素**，每次嘗試消耗那 1 個高階元素（魔法不消耗）。這五組輸入目前都沒有被任何配方使用（已檢查：`fire_pure_2` 是 `flame_burst + el:fire:3`，不衝突）。
- **成本檢查**：平均 65 次 × 每次 1 個高階元素（1 個高階＝30 個初階）是很大的投入。接手者要用 `tests/sim` 的機器人量出「學會該屬性 Lv.5 魔法時，每模擬分鐘大約能累積幾個高階元素」，換算平均要刷多久才合得出一個稀有魔法，記進帳本。若平均超過 **120 模擬分鐘**，不要自行改權重或成本，先記成待使用者決定的事項。【我的決定】**結果（2026-10-24）：** 1 : 64 時量到 139～211 分鐘；使用者決定稍微提高機率（1 : 49）並接受其餘長度，量到 火 107、風 128、雷 122、土 162、水 141 分鐘，`tests/sim/rare-cost.test.ts` 的上限改為 180 分鐘並恢復執行。
- **落空提示（2026-10-24 使用者要求）：** 機率配方落空、而且這個組合還可能擲出玩家尚未學會的魔法時，合成台下方提示「這個組合似乎還藏著別的可能……多試幾次，也許會有不一樣的結果。」；不提魔法名稱。判斷在用戶端用引擎的 `rareStillHidden`（擲骰前的狀態、只算前置條件已滿足的結果）。
- 階級 **Lv.8**：同時期的 Lv.7 純屬性名魔法（墜日等）攻擊 70，稀有魔法攻擊約 **80**，冷卻與效果組合讓整體輸出比同屬性 Lv.7 高約 15～20%；仍低於 Lv.9 的聖光審判、深淵吞噬。確切數值由接手者照現有的平衡方式定，但要守住第 6 節的限制。
- 效果只用現有的效果種類（`bolt`、`ring`、`blades`、`chain`、`zone`、`storm`、`meteor`、`field`、`haste`）組合，不新增引擎效果種類；每個稀有魔法要有自己一眼可辨的組合（例如焚世之焰＝全場 `field` 點燃＋多顆 `meteor`；蒼穹之息＝大範圍 `zone` 拉扯＋`blades`；九天雷獄＝長時間 `storm`＋多跳 `chain`；泰坦之握＝`ring` 擊退＋強力單體 `bolt`＋暈眩；滄溟月潮＝持續 `zone`＋`field` 減速）。
- 每個稀有魔法都要有殘卷線索（`hint`），線索暗示「Lv.5 純屬性魔法＋高階元素、而且要多試很多次」，但不直接寫出配方。
- 名稱、說明、`nameEn`、`words`（自創魔法命名用）照現有 `spells.json` 格式補齊；`named: true`、`affinity: "self"`。
- 魔導書節點：5 個稀有魔法放在魔導書上（`node`），位置在各自 Lv.5 魔法的外側，屬於現有的區域，不新增迷霧區域；跟其他未學會的魔法一樣只顯示名稱與殘卷線索。確切的 `ring`／`angle` 由接手者照 `grimoire-layout` 擺放，不能和現有節點重疊。

### 2.2 哪些魔法算「稀有」【我的決定】

- 在 `spells.json` 加一個選填欄位 `rare: true`。
- 標記為稀有的魔法：上表 5 個新魔法，**加上**現有的聖光審判、深淵吞噬（它們同樣是高階、機率取得，符合使用者的條件）。這兩個魔法的數值與配方不變，只是合出來時也會播全螢幕動畫、上資訊欄。
- 規則上「稀有」只看這個欄位；`content.ts` 的交叉檢查要確認：每個 `rare` 魔法都只出現在至少有一個 `spellId: null` 落空結果的配方裡（也就是一定是機率取得）。

## 3. 發現者看到的：全螢幕動畫【使用者決定，草圖 `2026-10-23-rare-fullscreen.html`】

- 合成台照常播融合特效（`MIN_FUSE_MS`）；結果是稀有魔法時，不在合成台中央揭曉，改由**全螢幕動畫**接手：
  1. 0～1 秒：畫面變暗，合成台的光球飛到畫面中央，凝聚成該屬性顏色的光環。
  2. 1～2 秒：光環爆開，全畫面放射該屬性的粒子（沿用 `element-fx.ts` 的顏色與形狀語彙），輕微震動。
  3. 2～4 秒：大字揭曉——元素點、名稱、`Lv.N`、「稀有魔法」、殘卷線索。**全服第一位**合出的人看到「✦ 全服首次發現 ✦」，之後的人看到「✦ 稀有魔法！✦」。
- 約 4 秒，點一下跳過（第 3 階段點一下關閉）；`prefers-reduced-motion` 時跳過粒子與震動，直接顯示第 3 階段。
- 稀有魔法照現狀自動裝備；戰鬥畫面的「新發現！」橫幅在全螢幕動畫期間不另外顯示。【我的決定】
- 「是不是全服第一位」由伺服器在合成時判斷，跟著合成結果一起回傳（第 5 節）。

## 5. 伺服器與資料【我的決定】

- 新 migration `0005_discoveries.sql`（**不能重置存檔**）：

```sql
CREATE TABLE discoveries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  spell_id TEXT NOT NULL,
  player_id TEXT NOT NULL REFERENCES players(id),
  display_name TEXT NOT NULL,   -- 發現當下的顯示名稱快照
  at INTEGER NOT NULL,
  first INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX discoveries_first ON discoveries(spell_id) WHERE first = 1;
CREATE INDEX discoveries_recent ON discoveries(id DESC);
```

- 合成動作（`worker/app.ts` 的 synthesize）結果是 `learned` 且該魔法 `rare` 時，在同一個交易裡寫一筆 `discoveries`：
  - 該魔法還沒有 `first = 1` 的紀錄、而且玩家不是可疑帳號（`players.suspicious = 0`）→ `first = 1`。部分唯一索引保證兩人同時合出時只有一位是首位。
  - 可疑帳號的發現**不寫入** `discoveries`（不上清單、不當首位）；上層規格 4.12、4.14 的精神。
  - 同一位玩家只會 `learned` 一次（之後是 `duplicate`），所以每人每個稀有魔法最多一筆。
- 合成回應的 `learned` 結果多一個欄位 `rare?: { first: boolean }`（只有稀有魔法才有）。`ActionResult` 型別、`api.ts` 解析、`messages.ts` 照著擴充。
- 新端點 `GET /api/discoveries?after=<id>`：回傳最近的發現（最多 20 筆，`id`、`spellId`、`displayName`、`at`、`first`），依 `id` 由新到舊；需要 session（與其他 API 相同的驗證）。不回傳 `player_id`。
- `Store` 介面加兩個方法（例如 `recordDiscovery`、`recentDiscoveries`），`MemoryStore` 與 `D1Store` 都要實作，並加進 `store-contract.ts` 的共用契約測試；`tests/d1` 加 migration 0005 的測試（套用後舊存檔還在）。
- 首位發現者紀錄就是 `first = 1` 的那幾列；排行榜（第二版 C+D）之後直接讀它。
- **寫入時機**：`discoveries` 在存檔寫入成功**之後**才寫（409 衝突或 422 被拒時什麼都不寫）。兩次寫入之間不是同一個交易，萬一伺服器在中間當掉，最多少記一筆發現；「只有一位首位」由部分唯一索引保證，不靠交易。插入首位時若撞到唯一索引，就改寫成 `first = 0` 的一筆。這個小窗口可以接受（沒有真實玩家、事件極少）。
- **`rare.first` 以資料庫為準**：由這次是否成功寫入 `first = 1` 決定，不看存檔。
- **回應遺失**：存檔已寫入但用戶端沒收到回應（斷線）時，玩家下次看到的是已學會的魔法、沒有全螢幕動畫；資訊欄仍會有紀錄。可以接受，不做補播。
- **不回填**：migration 0004 已重置所有存檔，遠端從未部署、沒有真實玩家，所以已經會聖光審判或深淵吞噬的存檔不需要回填 `discoveries`。
- **顯示名稱**：用 `players.display_name`（玩家進遊戲時自己輸入的名稱），不顯示帳號的登入名稱 `username`（那是登入用的識別，不公開）。React 會跳脫文字；長度沿用現有的顯示名稱驗證上限。
- **`after` 的意思**：`GET /api/discoveries` 不帶 `after` 時回傳最新 20 筆；帶 `after=<id>` 時只回傳 `id` 比它大（更新）的紀錄，最多 20 筆。用戶端用它輪詢新消息。

## 6. 不能違反的規則（摘自 `AGENTS.md` 第 6 節，與本次相關）

- **伺服器是銀行**：稀有魔法只能由伺服器擲骰合成取得；`learned` 只由伺服器改變。
- **專精路線不能被內容卡住**：新增的配方與魔法不能改變現有路線；`tests/sim` 各路線通關時間 60～240 模擬分鐘、0 次被拒。模擬機器人不必去追稀有魔法。
- **隨機配方的重試不免費**（R14、R14b）：落空到已會的自創魔法時照現有規則扣成本。
- **自創魔法 id 只有一種寫法**（R4）：落空結果仍是 `craftedId` 規則產生的 id。
- **特效上限** `MAX_ACTIVE_FX = 24`：稀有魔法的戰鬥特效不能繞過。全螢幕動畫是 React／CSS 層，不算戰鬥特效，但不能讓 Pixi 戰鬥掉幀。
- **React 效能**：鈴鐺與清單用窄 selector，不訂閱整個 `game`。
- **「Lv.」永遠是階級**；介面文字繁體中文；資料名稱附 `nameEn`。
- **不收集 email**；資訊欄只顯示顯示名稱。

## 8. 驗收

1. `content.ts` 載入 5 個新魔法與 5 個新配方，交叉檢查通過；每個 `rare` 魔法都是機率取得。
2. `tests/sim` 各路線通關時間仍在 60～240 模擬分鐘、0 次被拒。
3. 合成 `inferno + el:fire:3`：落空時照常得到自創魔法；以注入的亂數（`createApp` 的 `deps.rng`）讓結果是焚世之焰時，回應帶 `rare.first = true`，`discoveries` 寫入一筆 `first = 1`；第二位玩家合出時 `rare.first = false`、寫入 `first = 0`。
4. 兩位玩家同時合出同一個稀有魔法，只有一位是首位（唯一索引）。
5. 可疑帳號合出稀有魔法：照常學會，但不寫入 `discoveries`、回應 `rare.first = false`。
6. 瀏覽器：合出稀有魔法時播全螢幕動畫（首次與非首次文字不同），點一下可跳過，結束後魔法已裝備。
7. 另一個視窗（另一位玩家）在 60 秒內看到鈴鐺亮起未讀數字；打開清單看到名稱、殘卷線索、發現者顯示名稱與時間，沒有配方。
8. 套用 migration 0005 後，本機既有存檔仍在。
9. `npm test` 與 `npm run build` 通過。
