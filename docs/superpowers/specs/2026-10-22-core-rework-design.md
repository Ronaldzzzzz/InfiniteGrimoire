# 核心重做：成群魔物、元素組合魔法、迷霧技能樹

- 日期：2026-10-22
- 狀態：設計討論完成，待使用者審閱
- 依據：使用者試玩後的回饋，以及拋棄式原型 `docs/design/mockups/combo-prototype.html`（直接用瀏覽器打開就能玩）
- 與上層規格的關係：本文件**取代**上層規格（`2026-10-21-infinite-grimoire-design.md`）中戰鬥（4.1）、合成（4.3）、魔導書（4.4 的五屬魔導書部分）的做法。上層規格其他部分（伺服器是銀行、不收 email、配色等）照舊。衝突時以本文件為準。

標記說明：**【使用者】** 是使用者在討論中決定的；**【我的決定】** 是設計者代為決定、使用者可以推翻的；**【交給開發者】** 是實作時自行決定的。

## 1. 為什麼要重做

使用者試玩 MVP 的原話：「打怪太無聊、技能樹太無聊、合成也偏無聊。打開的瞬間就已經可以看得到遊戲的盡頭了。」

問題的根源：
- 戰鬥是一次打一隻、數字很小，沒有爽快感。
- 合成只有固定幾種配方，合出來就是終點，不能再合。
- 技能樹從一開始就整張攤開，玩家一眼看到全部內容。

使用者喜歡的參考：**Infinite Craft**（什麼都能合、合出來還能再合、結果出乎意料）與 **Cookie Clicker**（永遠有「下一個新東西」）。

## 2. 目標體驗【使用者】

玩家最常說的話應該是：「**哇，居然合得出這個，我真的是操控元素的大魔法師。**」

原型驗證過的爽點（使用者原話）：「合成出特殊魔法並清空畫面的魔物的時候：哇真爽！還有屬性搭配的特效！」

長期的玩法：玩上**幾週**。上班時放著掛機享受殺怪快感、每天上線一下看進度、有更新再回來；目標是取得強力魔法、衝榜、爬塔等小遊戲。本文件只處理第 1 步（見第 3 節），但設計要為幾週的長度留空間。

## 3. 範圍

整體拆成四步，依序進行【使用者同意】：

1. **核心重做（本文件）**：成群魔物、元素特性與特效、名魔法與自創魔法、相性、可以一直往下合、固定但有迷霧並靠關鍵道具拓展的技能樹。
2. 離線收益與掛機（讓「每天看一下」成立）。
3. 內容擴充（地點、材料、名魔法，持續追加）。
4. 爬塔、排行榜等（排行榜原本是第二版 C+D）。

**使用者允許大幅重做**現有的戰鬥、合成、技能樹與相關的伺服器檢查。帳號、session、存檔上傳／同步、斷線處理等基礎建設保留。

### 非目標（第 1 步不做）
- 離線收益、爬塔、排行榜、煉金系統、商店金幣、光暗魔導書的完整內容。
- 同時裝備多個魔法（先維持 1 格）【我的決定】。
- 在遊戲裡即時呼叫 AI 產生內容【使用者：不想付 AI 費用】。

### 反目標（做了就算失敗）
- 一打開就看得到全部內容或盡頭。
- 合成結果全部可以預測、沒有懸念。
- 魔法換上去後戰鬥看起來差不多（「很威」的感覺沒有出來）。
- 只有數字變大，沒有新的行為或特效。

## 4. 戰鬥

### 4.1 成群魔物【使用者：「怪物成群被秒殺」】
- 圓形戰場（沿用 `src/render/arena.ts` 的幾何），小人在中心，魔物從邊緣成群湧入、往中心走，到停止圈後停住（沿用 MVP 的徘徊動作）。
- 場上同時存在的魔物數量大幅提高：原型是上限 170 隻、平時 30～100 隻。實際數字【交給開發者】，但目標是讓範圍魔法有「一次清掉一片」的空間。
- 除了零星生成，定期出現**成群**（同一方向一次 10 隻以上），讓範圍魔法有聚集的目標。
- 魔物強度隨地點提高；基礎魔法清不完、場上會累積魔物，組合魔法才能清場——這個落差就是「換上新魔法」的爽感來源（原型已驗證）。
- 小人**沒有血條、不會死**（上層規格不變）。魔物堆在中心不會造成失敗。
- 單體高傷的魔法保留，用來打魔王。

### 4.2 戰鬥改成 2D
- MVP 的引擎戰鬥是一維（`x` 由外往內）。改成**二維座標**，因為聚怪、擊退、龍捲把怪吸到中心、範圍爆炸都需要位置。
- 戰鬥模擬仍放在 `src/engine/`（純 TypeScript、固定步進、可用固定亂數重現），畫面在 `src/render/` 讀取引擎狀態並補間（沿用 `stepAlpha()`）。
- 效能目標：桌面瀏覽器在上限魔物數＋最重的組合魔法下維持流暢（約 60fps）【交給開發者：量測方式沿用試玩修正時的卡頓量測】。

### 4.3 一網打盡的回饋
- 短時間內大量擊殺時，畫面上方顯示「×N 一網打盡！」（原型：0.8 秒內 6 隻以上）。
- 大魔法有畫面震動、施法名稱浮字、小人身上的元素光。

## 5. 元素與魔法行為

### 5.1 五個元素的特性【我的決定，原型已驗證】
| 元素 | 特性 | 原型中的基礎魔法 |
|---|---|---|
| 火 | 燃燒（持續傷害）；燃燒中的怪死掉會把火傳給旁邊的怪 | 火球：命中爆開並點燃 |
| 風 | 擊退或聚集、範圍大 | 疾風刃：向外甩出風刃並擊退 |
| 雷 | 在怪之間跳躍；打到「濕」的怪傷害加倍 | 落雷：連鎖閃電 |
| 土 | 暈眩、重擊、地形 | 岩槍：在怪最多的地方突出、暈眩 |
| 水 | 減速、讓怪變「濕」 | 水波：擴散、減速、打濕 |

狀態效果至少有：燃燒、濕、減速、暈眩、凍結（受到傷害 ×1.5）、失明（亂走）、回血（反效果用）。小人自身的 buff／debuff 至少有：施法加速、施法減速（視線受阻）、暈眩（反噬）。

### 5.2 魔法由「效果積木」組成【我的決定】
為了讓「組合出新行為」與「自創魔法可以無限組合」都做得到，魔法不再是 `pattern + attack` 幾個欄位，而是**一串效果積木加上參數**。原型裡的積木：投射物、爆炸、擴散環、連鎖、區域（持續 tick）、龍捲（吸怪＋移動）、雷雲（隨機落雷）、隕石（延遲落下＋熔岩）、全場狀態、小人 buff、反噬。

- 每個積木有傷害、範圍、持續時間等參數，以及施加的狀態。
- 名魔法是手工排好的積木組合，可以有專屬的積木或專屬的畫面。
- 自創魔法由兩邊魔法的積木組合而成（見 6.3）。
- 積木清單與參數格式【交給開發者】，資料仍放在 `src/data/*.json`，要能被引擎與伺服器共用。

### 5.3 特效要看得出元素【使用者】
- 畫面要「充分呈現火屬性與風屬性的特效與特性」：組合魔法同時帶有兩邊元素的顏色與形狀（例如火焰龍捲是風的旋轉形狀＋火的顏色與火星）。
- 每個元素有自己的粒子／形狀語言（原型：火＝橘色火星往上飄、風＝青色弧線、雷＝黃白鋸齒線、土＝褐色碎片、水＝藍色環與水滴）。
- 美術先用程式畫的粒子與形狀，選用貼圖機制（`public/assets/<key>.png`）保留。

## 6. 合成

### 6.1 什麼都能合【使用者】
- 合成槽 2 格。可以放：**已學會的魔法**與**材料**。
- **元素與基礎魔法的關係**【我的決定】：玩家一開始就會五個元素的基礎魔法（火球、疾風刃、落雷、岩槍、水波），合成槽裡放的是「魔法」。元素是掉落的**燃料**，不放進槽，而是在合成時被扣掉（見 6.6）。所以「火球＋疾風刃＝火焰龍捲」，原型裡「點元素按鈕」等同於放進該元素的基礎魔法。這也讓配方只有一種查法：兩個輸入都是魔法 ID 或材料 ID。
- 合出來的魔法可以再拿去合，一直往下挖【使用者：「兩個都要，合出來的能再合，魔法也要在戰鬥中很威」】。

### 6.2 名魔法與自創魔法【使用者】
- **名魔法**：世人熟知、大家都在學的魔法，畫在技能樹上，配方是固定的。每個名魔法有手工設計的行為與特效。
- **自創魔法**：自己摸索出來、世上沒有記載的魔法，**不會標在技能樹上**，記在玩家自己的「魔法筆記」裡。由規則自動產生，數量無限。
- 自創魔法**不一定比名魔法弱**【使用者】。
- 一組輸入如果有對應的名魔法配方，就得到名魔法；沒有的話，就得到自創魔法。
- 配方表要讓玩家亂合時偶爾「撞中」樹上還沒點亮、甚至還在迷霧裡的名魔法【我的決定】（例如原型的「蒸氣＋雷＝雷雨雲」：失敗作也值得留著）。

### 6.3 自創魔法的產生規則【我的決定，原型版本】
- 名稱：由兩邊魔法的「形容詞」與「名詞」拼成（原型：`A 的 pre` ＋ `B 的 noun`，例如「雷火浪潮」）；相性差時加上「失控的」。每個名魔法與元素都要有 pre／noun 兩個字詞。
- 行為：兩邊魔法的效果積木一起發動，依相性乘上倍率。
- 相性：依兩邊包含的元素兩兩查相性表加總，結果是「極佳／奇妙／差」三種。
- 冷卻：由兩邊冷卻推算。
- **同一組輸入永遠產生同一個自創魔法**（同名、同效果），由輸入的 ID 決定（見 6.5）。
- **深度**：基礎魔法深度 0，合成結果的深度＝兩邊較深者＋1（材料算 0）。超過目前的**深度上限**時變成「魔力過載」：小人自己暈倒。
- **深度上限會成長**【我的決定】：一開始較低（例如 3），靠技能樹的被動節點或關鍵道具逐步提高。這樣「往深處挖」本身就是長期成長的一部分，不是一道死牆；上限以內則可以任意往「寬」挖。
- **材料參與自創魔法**【我的決定】：「魔法＋材料」＝該魔法的變體，材料的特性變成一個附加的效果積木或參數修飾（例如雷鳥羽毛＝多一段連鎖），並帶入材料的元素傾向參與相性計算。「材料＋材料」沒有名魔法配方時「沒有反應」，**不消耗**任何東西。
- **平衡上限**【交給開發者，但要寫成可測的規則】：每多疊一層，增幅遞減；強度要有天花板，避免疊出讓所有地點都失去意義的魔法。「不一定比名魔法弱」代表：懂相性、搭得好的深層自創魔法**可以**超過同層的名魔法，但不能無限成長。

### 6.4 相性【使用者】
- 相性好的組合會**加成傷害**。
- 相性差的組合**有時候會有反效果**，或變成 **buff／debuff**。
- 原型的相性表（【我的決定】，可調）：
  - 好：火＋風、水＋雷、風＋雷、土＋火、水＋風、火＋雷
  - 差：火＋水、土＋雷
  - 其他：奇妙（同時發動、無倍率，或特殊效果）
- 相性差的反效果例子（原型）：蒸氣（火被澆熄、怪回血、施法變慢）、接地（雷被吸收；30% 機率變成磁化岩爆）、自創魔法 30% 機率反噬讓小人暈眩。

### 6.5 固定與隨機【使用者】
- **大部分配方固定**：同樣兩樣東西，每個人每次都合出同一個結果。
- **少數特殊配方帶隨機性**，用來解鎖特殊魔法、獨特魔法、光暗魔法等。合了不一定成功。
- 失敗時不白合：得到一般結果或退回部分材料【我的決定】。

### 6.5.1 階級規則【我的決定】
- 保留 MVP 的**傷害門檻**（魔法階級 ≥ 魔物階級 − 1，或攻擊力 ≥ 防禦 × 0.7，否則傷害為 0、顯示「無效」）與**越級遞減**（AGENTS.md 第 6 節）。地點仍靠「打不動」擋住玩家，再加上「清不完、場上累積」的壓力；伺服器判斷「這個魔法打不打得到這隻怪」的方式也延續。
- 自創魔法的階級由兩邊推導（例如較高者，相性極佳時 +1），公式要可測，並受強度天花板約束。
- 擲骰一律在**伺服器**（沿用現有 `/api/synthesize` 的伺服器擲骰）。

### 6.6 合成消耗【我的決定】
- 放進槽的元素與材料會被消耗；**魔法是知識，不會被消耗**。
- 因為魔法不消耗，「魔法＋魔法」也要有成本，否則可以無成本無限產生自創魔法：每次合成另外消耗與結果元素對應的元素量，疊得越深消耗越多。實際數字【交給開發者】，目標是「合成」與「去打怪存元素」互相推動。
- 已經學會的結果再合一次：退回部分消耗（沿用 MVP 的重複退還精神）。
- 已嘗試過的組合要記錄，並在介面上標示（沿用 MVP 的嘗試紀錄與組合表，資料結構可改）。

## 7. 技能樹

### 7.1 固定、迷霧、往外拓展【使用者】
- 技能樹的**節點與連線事先固定**，每個人的樹都一樣（「為求簡單，真正的技能樹還是需要固定」）。
- 玩家一開始只看得到中心一小塊，外圍被**迷霧**蓋住。
- 打到**關鍵道具**時，樹會**向外拓展**：迷霧散開，露出新的節點。
- 節點就是**名魔法**，靠**合成點亮**。
- 節點也包含**被動能力**；被動能力可以搭配掉落物、特定條件，以及之後的煉金系統來解鎖【使用者】。第 1 步至少做「掉落物」與「特定條件」兩種解鎖方式；煉金之後再接。
- 迷霧裡的節點：配方完全看不到；剛露出的節點：可以看到名字或輪廓與殘卷線索（沿用 MVP 殘卷線索的精神）【我的決定】。

### 7.2 版面
- 沿用上層規格的五屬放射狀概念（中心向外、每個屬性一塊），**單一元素的純屬性路線**保留（例如火＋火→烈焰爆發），讓只玩一種屬性的玩家也能前進【我的決定，承接上層規格的「專精路線不能被內容卡住」】。
- 組合魔法放在相關屬性之間。上層規格的五芒星（不相鄰混合）與相鄰混合的排版可沿用或調整【交給開發者】，但必須能表現「一圈一圈被迷霧揭開」。
- 介面支援縮放與拖曳（沿用 `GrimoirePanel`）。

### 7.3 魔法筆記
- 自創魔法列在獨立的「魔法筆記」，可以裝備、可以拿去合成，顯示名稱、元素點、相性標籤與說明（原型右側的魔導書列表即是雛形）。

## 8. 材料、關鍵道具、地點

- **元素**：主要由一般魔物掉落，數量多，是合成的基本燃料。MVP 的元素等級（`el:<元素>:<1-3>`）可保留或簡化【交給開發者】。
- **材料**：一般掉落、比元素稀有，每種材料帶有元素傾向與一個特性（例如「雷鳥羽毛」帶雷、偏向連鎖），可以參與名魔法配方，也能和魔法合成自創魔法【我的決定】。
- **關鍵道具**：稀有，通常由魔王或新地點的特定條件取得，用途是**拓展技能樹**（散開迷霧），也可以解鎖新地點或新材料。
  - **使用方式**【我的決定】：關鍵道具先進背包（跟一般掉落一樣經過上傳檢查）。玩家在技能樹上按「使用」，呼叫新的伺服器 API；伺服器確認背包裡有、扣掉、記錄拓展，回傳後播放迷霧散開的動畫。用掉就消失。
- **地點**：越遠的地點魔物越強、掉落新材料與關鍵道具。第 1 步的地點數【交給開發者】，至少要讓玩家體驗到「拿到關鍵道具 → 樹往外長 → 新配方 → 打得過下一個地點」完整一輪以上。
- 要打過更強的魔物，就得合出更強的魔法——合成與打怪互相推動【使用者同意】。

## 9. 內容量與節奏

- 長期目標是**幾週**；第 1 步先做出能驗證核心循環的內容量：五個元素的所有兩兩組合（含同元素）都有名魔法、第二層以上的名魔法若干、材料與關鍵道具若干、樹至少能往外拓展兩次以上。具體數量【交給開發者】，但資料結構要能擴充到上層規格的規模（每屬性 50 個以上節點）。
- 第 1 步的節奏以「一次遊玩數小時」來調；配合每天上線的長節奏在第 2 步（離線收益）重調【我的決定】。
- 內容（名魔法、材料、配方、殘卷文字）可以在開發時大量手寫進 JSON，不在遊戲中使用 AI【使用者】。

## 10. 伺服器與防作弊

伺服器是銀行（上層規格 4.12）不變：
- `learned`（名魔法與自創魔法）、合成紀錄、關鍵道具造成的技能樹拓展，只能由伺服器改變。
- 自創魔法要讓伺服器與瀏覽器用**同一套引擎函式**由輸入 ID 推導出相同的魔法定義；存檔只需存 ID。
- 上傳存檔的增益檢查（`validate.ts` 的錨點窗口）要依新的生成速度、成群生成與掉落表重寫。原則不變：正常遊玩 0 次被拒、作弊的上傳被拒。
- `tests/sim` 的模擬機器人要改成新系統：經由真實 API 遊玩，0 次被拒，且能打通第 1 步的所有地點。worker 的對抗測試照樣要通過。
- 安全性與防作弊做到合理即可（使用者 2026-10-22 指示），不追求滴水不漏。

## 11. 存檔與既有資料

- 存檔格式改成新版本（`version: 2`）。目前沒有真實玩家，**舊的 version 1 存檔直接重置成新的初始狀態**，帳號與 session 保留【我的決定】。
- 合成紀錄、`synth_events` 等資料表可依新系統調整；需要的話新增 migration。

## 12. 介面

- 版面沿用試玩修正後的三欄（戰鬥｜魔導書｜元素表＋合成），內容換成：合成槽可以放元素、材料、魔法；魔導書顯示迷霧技能樹；另有魔法筆記（自創魔法）。實際配置【交給開發者】，手機寬度（360px）不能有橫向捲動（沿用既有驗收標準）。
- 合成結果要有「新發現！」的展示（原型：戰場中央的橫幅，顯示名稱、元素點、相性標籤、說明），合出後自動裝備【我的決定，原型行為】。

## 13. 交給開發者的事項（彙整）
- 魔物數量上限、生成節奏、強度曲線、所有數值。
- 效果積木的清單、參數格式與資料檔結構。
- 自創魔法的增幅遞減與強度天花板公式（要可測）。
- 合成成本的數字。
- 技能樹的具體排版、第 1 步的地點與內容數量。
- 元素等級是否保留。
- 效能量測方式。

## 14. 驗收

- 自動化：`npm test`、`npm run build` 通過；`tests/sim` 新版機器人 0 次被拒並打通所有地點；worker 對抗測試通過；引擎測試涵蓋自創魔法的確定性（同輸入同結果）、相性、深度上限、強度天花板。
- 畫面：headless 瀏覽器確認 1280／360 寬版面、合成「新發現」展示、迷霧拓展。
- **使用者試玩**：核心判準是使用者是否再次說出「哇真爽」。使用者表示會等成品出來再討論還不對的地方。
