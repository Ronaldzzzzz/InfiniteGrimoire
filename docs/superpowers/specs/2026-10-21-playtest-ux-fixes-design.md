## 1. 為什麼要改

使用者試玩時描述的實際操作：

> 原先在看魔導書，但想合成時，需先按右上方合成 tab，正下方合成元素，點擊元素，再回到右上方按下合成。

也就是說，一次合成要在「右上分頁 → 正下方元素列 → 右上合成按鈕」之間來回跑三趟，而且要先離開魔導書。這和北極星「玩家一直在想下一步怎麼合成」直接衝突：合成太麻煩，玩家就不會一直嘗試。

使用者回報的四個問題：
1. 戰鬥畫面太大，擠壓元素列表，合成很困難。
2. 元素列表沒有分類，而且離合成介面太遠。
3. 戰鬥畫面改成：小人在圓心，怪物以隨機方式往圓心前進，但不會與小人重疊。
4. 畫面有些微卡頓，不確定是電腦還是遊戲引擎的問題，待查。

**目標**：從「在魔導書看到想要的魔法」到「按下合成」，手和眼睛都只在一個面板裡移動。

**非目標**：不改合成規則、機率、伺服器驗證、存檔格式、數值平衡。

**反目標**：
- 改完之後合成仍要切分頁或跨越畫面兩端。
- 戰鬥畫面縮小後，看不出魔法差異（違反上層規格「每個魔法一眼可辨」）。
- 「無效」等關鍵回饋小到看不清楚。

## 2. 新版面（B 案）【使用者決定】

### 2.1 寬螢幕（桌面）

```
┌──────────────────────────────────────────────────────────────┐
│ 頂列：📍地點下拉 ▾ │ 裝備：雷電術 │ 越級提示 │ 魔王打不動提示 │ 存檔狀態 │
├──────────────┬────────────────────────┬──────────────────────┤
│              │                        │ 元素表（分類）        │
│   戰鬥畫面    │       魔導書            │──────────────────────│
│  （圓形戰場）  │   （五屬扇形 SVG，      │ 合成槽 ＋ 合成按鈕     │
│              │    可縮放／拖曳）        │──────────────────────│
│              │                        │ 殘卷線索              │
│              │                        │ 嘗試紀錄              │
└──────────────┴────────────────────────┴──────────────────────┘
     約 1/3                 右側面板約 2/3（內分兩欄）
```

- **【使用者決定】** 魔導書與合成放在同一個側邊面板，面板內分兩欄：左欄魔導書；右欄由上到下是元素表、合成槽與按鈕、殘卷線索、嘗試紀錄。元素表緊貼在合成槽正上方。
- **【使用者決定】** 拿掉「合成／魔導書／地圖」三個分頁。地圖改成頂列的地點選擇器（自製彈出清單，不是原生下拉選單，內容見第 2.4 節），鎖住的地點顯示為不可選。
- **【使用者決定】** 戰鬥畫面約佔左側 1/3，右側面板約 2/3。
- **【使用者決定】** 頂列顯示：目前地點、裝備中的魔法、越級遞減提示、打不動魔王的提示、存檔失敗提示（沿用現有的 `SaveErrorBanner` 行為）。

### 2.2 互動

- **【使用者決定】** 元素表點格子 → 放進第一個空的合成槽；點合成槽 → 退回元素表。合成按鈕的啟用條件不變：兩格都有東西、數量足夠、沒有合成進行中。
- **【使用者決定】** 在魔導書點未學會的魔法：它的殘卷線索顯示在合成槽旁邊的「殘卷線索」區，方便對照著試。點已學會的魔法：直接裝備，和現在一樣。
- **資料來源（現有程式）**：
  - 「嘗試紀錄」就是現在 `src/ui/SynthesisPanel.tsx` 裡以 `game.synthesisLog` 畫出的清單（每個組合的嘗試次數、各結果的出現頻率、「無反應」標籤），只是搬位置，不需要新資料。
  - 「殘卷線索」是 `gameData.spells[id].hint`，目前是 `src/ui/GrimoirePanel.tsx` 內部的 `hint` 狀態。**【我的決定】** 這個狀態提升到面板的共同父元件（例如新的 `SidePanel` 或 `App`），讓魔導書和合成區共用；線索持續顯示，直到點了別的魔法節點或成功學會該魔法為止。
- **【使用者決定】不用原生 `<select>` 下拉選單**：使用者回饋原生下拉選單體驗不好，看不到魔法的階級，也不能依屬性排序。**規則：凡是用下拉形式的選擇器，打開後都要能正確顯示做決定需要的資訊**（見第 2.4 節）。原生 `<select>` 只能顯示一行文字，所以裝備選擇和地點選擇都改成自製的選擇器（按鈕＋彈出清單）。
- **【我的決定】** 寬螢幕移除頂列的裝備選擇器，因為魔導書已經能裝備；**窄螢幕（< 768px）保留**在頂列，因為那時魔導書排在合成區下方，換裝備不該需要捲動。窄螢幕保留的就是第 2.4 節的魔法選擇器，不是原生下拉選單。
- **【我的決定】** 面板空間不夠時，允許面板**垂直捲動**（禁止的只有橫向捲動）；魔導書本身可縮放，元素表與合成槽不縮放。

### 2.3 窄螢幕（平板直式、手機）【使用者決定】

- 寬度不夠時，面板兩欄改成上下排列：**先元素表與合成**，再往下才是魔導書。
- 手機上戰鬥畫面在最上方，高度約佔畫面的 1/4。
- 仍需符合上層規格：360px 寬可用、沒有橫向捲軸、全部操作可用點擊完成。

**【待決策】斷點數值**：建議 ≥ 1100px 用三欄（戰鬥｜魔導書｜元素＋合成）；768～1099px 用兩欄（戰鬥在上一列，下方面板兩欄）；< 768px 全部上下排列。接手者可依實測調整。

### 2.4 選擇器要顯示的資訊【使用者決定：資訊要能正確顯示；欄位與排序是我的決定】

現況：`src/ui/Hud.tsx` 的裝備選單是原生 `<select>`，只列出魔法名稱，順序是學會的順序；`src/ui/ZonePanel.tsx` 的地點是按鈕清單，只有名稱與鎖頭。

**魔法選擇器**（窄螢幕頂列；寬螢幕不顯示，改由魔導書裝備）：
- 每一列顯示：屬性色塊（混合魔法顯示兩色）、魔法名稱、**階級**、攻擊型態（`bolt` 單體／`beam` 光束／`chain` 連鎖／`nova` 擴散）、攻擊力。
- 對目前地點的效果標記（用現有的 `canDamage` 與 `overlevelEfficiency` 算，不新增規則）：打不動目前魔王時標「對魔王無效」；越級遞減時標效益百分比，例如「掉落 75%」。
- **排序**：預設**依屬性分組**（依 `ELEMENT_ORDER`；混合魔法放在最後的「混合」組），組內依階級由低到高。提供一個切換鈕改成**依階級**排序（全部魔法由高到低）。排序選擇存在 `localStorage`（讀寫都包 try/catch，失敗就用預設）。
- 目前裝備的那一列要醒目標示；點一列就裝備並關閉清單。
- 只列出已學會的魔法；未學會的魔法在魔導書裡看。

**地點選擇器**（頂列，所有寬度都有）：
- 每一列顯示：地點名稱、一般魔物的階級範圍、魔王名稱與階級、狀態（目前所在／已擊敗魔王／可前往／未解鎖）。
- 未解鎖的地點不能選，顯示「擊敗〇〇後解鎖」（〇〇是前一個地點的魔王名稱）。
- 依 `zone.order` 排序。

**兩者共通**：
- 收合時按鈕上顯示目前的值和最重要的一項資訊（魔法：名稱＋階級；地點：名稱＋階級範圍）。
- 點擊開關；點清單外或按 Esc 關閉；鍵盤可用上下鍵移動、Enter 選擇。
- 360px 寬時清單不能超出畫面，不能造成橫向捲動；清單太長時清單本身垂直捲動。
- 需要測試：魔法依屬性分組與依階級排序的順序、效果標記、未解鎖地點不能選。

## 3. 元素表分類【使用者決定】

- 表格形式：**一列一個屬性**（依 `ELEMENT_ORDER`：火、風、雷、土、水，名稱用屬性色），**一欄一個階級**（初階、中階、高階），格子內是數量。
- 每列尾端有「升階」按鈕；當該屬性某一階數量 ≥ 3 而且還沒到最高階時才能按。
- **【待決策】** 升階按鈕的操作：一列可能同時有兩個階級可以升（例如初→中、中→高都夠）。建議按鈕升「最低可升的階級」，或在每個格子上加小的「↑」按鈕。前者簡單，後者精準。
- 素材（`mat:*`，目前只有魔晶）另外一列，顯示名稱與數量。
- 數量為 0 的格子變暗但保留位置，讓表格形狀固定，玩家能記住位置。
- 物品名稱沿用 `src/ui/messages.ts` 的 `itemName()`。

## 4. 圓形戰場

### 4.1 使用者描述的樣子【使用者決定】

- 小人站在**圓心**。
- 怪物從四周**隨機**出現，往圓心前進。
- 怪物**不會與小人重疊**。

### 4.2 建議做法【我的決定，接手者可調整】

- **只改畫面，不改引擎規則**：引擎的 `MonsterInstance.x`（1 = 遠、0.15 = 停止距離）保留為「離圓心的距離」，所以移動速度、停止點、目標選擇（最近的優先）、生成速率、防作弊上限都不變，`tests/sim` 與 worker 測試不受影響。
- 每隻怪物在生成時決定一個**隨機角度**，只用在畫面上：畫面座標 = 圓心 + 角度方向 × 距離 × 戰場半徑。
- **【使用者決定】戰場是正圓，而且可以大到超出戰鬥畫面**：戰鬥畫面不是正方形（桌面是直長條，手機是扁長條），使用者選擇維持正圓，超出畫面的部分直接裁掉，怪物從畫面外走進來。不用橢圓，也不為了正方形改版面比例。
- **【我的決定】半徑怎麼算**：戰場半徑 = 戰鬥畫面**長邊**的一半（從畫面中心量）。小人在畫面中心。怪物在 `x = 1` 生成，所以會在畫面外，沿直線走進來。
- **【我的決定】停止圈必須完整在畫面內**：停止距離對應的圓圈半徑要大於「小人半徑 + 怪物畫面半徑 + 間隙」，同時小於「短邊的一半 − 怪物畫面半徑」，確保停下來攻擊的怪物一定看得到、而且不壓到小人。如果固定的 0.15 換算後不在這個範圍內，畫面層改用夾在範圍內的停止半徑（只影響畫面，引擎的 `x` 不變）。
- **【我的決定】打到畫面外的怪物**：目標選擇是「最近的優先」，通常會打到看得到的怪物；如果目標還在畫面外，特效照樣畫（超出部分被裁掉），浮動數字和「無效」則夾到畫面邊緣內側顯示，玩家才看得到結果。
- **【我的決定】** 可以在戰場上畫出淡淡的停止圈，讓玩家知道怪物會停在哪裡。

**【待決策】角度要放在哪裡**：
- 選項 A（建議）：角度只存在畫面層（`BattleView` 用 `uid` 對應），引擎完全不動。缺點：重新整理後角度會重新隨機（戰鬥本來就不存檔，影響不大）。
- 選項 B：在 `MonsterInstance` 加 `angle` 欄位，用引擎的 rng 產生。優點：可以重現；缺點：要改引擎型別與測試。

**【我的決定】魔王的停止距離**：魔王畫面上是一般怪物的 2 倍大。停止距離改成依「小人半徑 + 該怪物的畫面半徑 + 間隙」換算，只影響畫面位置，引擎的 `x` 不變。驗收時以「任何怪物的外框都不與小人外框重疊」檢查。

**【待決策】怪物之間要不要避免重疊**：停在停止圈上的怪物可能疊在一起。建議做法是生成時把角度和現存怪物錯開至少 25°，畫面上再加一點分離位移；要不要做、做到什麼程度，由接手者決定。

**【待決策】特效在圓形戰場上的樣子**：
- `bolt`：從圓心射向目標，直接沿用。
- `beam`：目前打「最近的 2 隻」。在圓上兩隻可能方向不同，建議畫成從圓心射向第一隻的直線光束，第二隻另外畫一條較細的分支；或改成打同一方向扇形內的怪物（這會改規則，**不建議**在本次修正做）。
- `chain`：一隻跳一隻，沿用。
- `nova`：從圓心擴散的環，和圓形戰場天然契合，沿用。

### 4.3 尺寸與可讀性【使用者決定】

- 戰鬥畫面縮小後，特效和浮動數字依戰場大小等比例縮小。
- **「無效」浮字維持固定的可讀大小**（建議不小於 14px），不隨戰場縮小。

## 5. 卡頓（待調查）

### 5.1 使用者描述

畫面有些微卡頓，不確定是電腦還是遊戲引擎的問題。

### 5.2 已知的可疑點（從程式碼推測，**尚未量測**）

1. **React 每秒重新渲染整個 App 約 20 次（最可疑）**：`src/ui/App.tsx` 用 `useGame(runtime)` 訂閱整份快照，而遊戲每 50ms 前進一步就會產生新快照。這會讓 HUD、元素表、合成面板，以及整個魔導書 SVG（`GrimoirePanel` 也訂閱 `useGame`）每秒重畫約 20 次，即使它們顯示的東西沒變。
2. **每次命中都 `new Text(...)`**：`src/render/battle-view.ts` 的浮動數字每次命中都建立新的 Pixi `Text`，Text 會產生新的貼圖，命中頻繁時成本高。
3. **特效與血條每幀重畫 `Graphics`**：可能有不必要的清除與重畫。
4. **兩套迴圈**：`src/game/loop.ts` 的 requestAnimationFrame 推進遊戲，Pixi 自己的 ticker 也在跑，兩者可能沒有對齊。

### 5.3 調查方式【我的決定】

1. 在開發模式加一個 FPS／幀時間顯示（例如只在 `import.meta.env.DEV` 時顯示）。
2. 用 Chrome DevTools 的 Performance 面板錄 10 秒，找超過 16ms 的長幀，看時間花在 React 渲染、Pixi 繪製還是 GC。
3. 用 React DevTools Profiler 確認每秒的重新渲染次數。
4. 在另一台電腦對照，分辨是不是電腦本身的問題。

### 5.4 預期修法方向（依調查結果選用）

- 讓 React 只在「顯示用的資料」改變時才重畫：把 `useGame` 拆成小的 selector（例如 `useInventory`、`useLearned`、`useZone`），快照內容沒變就回傳同一個參考；戰鬥狀態只給 Pixi，不經過 React。
- 浮動文字改用物件池或 `BitmapText`，重複使用而不是每次新建。
- 血條只在血量改變時重畫。

**驗收標準【我的決定】**：在一般筆電上，戰鬥進行中與連續合成時都能維持接近 60fps，Performance 錄製中沒有超過 50ms 的長任務，React Profiler 顯示面板在戰鬥中不會每秒重新渲染多次。

**【待決策】** 如果量測發現是電腦本身的問題（例如另一台電腦很順），是否還要做上面的優化？建議至少做第 1 項，因為它的成本低、效益明確。

## 6. 不改的東西

- 遊戲規則、數值、配方、資料檔。
- 伺服器 API、存檔格式、防作弊驗證、錨點窗口。
- `tests/sim` 的五條路線測試必須繼續 0 次被拒。

## 7. 驗收

- 從魔導書看到想要的魔法，到按下合成，全程在同一個面板內完成，不需要切分頁。
- 1280px、768px、360px 三種寬度都沒有橫向捲軸，全部操作可用點擊完成。
- 圓形戰場：小人在圓心，怪物從隨機方向（包含畫面外）走進來，停在完整可見的停止圈上，不與小人重疊。四種魔法特效都能一眼分辨，「無效」清楚可讀。
- 選擇器：魔法選擇器看得到階級、屬性、攻擊型態與對目前地點的效果，能切換依屬性／依階級排序；地點選擇器看得到階級範圍、魔王與解鎖條件。全部不使用原生 `<select>`。
- 卡頓：依第 5.3 節量測，達到第 5.4 節的驗收標準，並在報告中附上量測前後的數據。
- `npm test` 與 `npm run build` 通過；新增的 UI 元件有測試（元素表點擊放入合成槽、升階按鈕啟用條件、魔導書點擊顯示殘卷線索）。
